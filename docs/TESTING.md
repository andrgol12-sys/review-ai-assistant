# Тестирование Review AI Assistant

Этот документ описывает подход к тестированию Review AI Assistant, обнаруженные в процессе разработки проблемы и принятые решения.

Цель тестирования — проверить не только техническую работоспособность приложения, но и корректность поведения ИИ-ассистента в типовых и критических сценариях.

---

# 1. Что проверяется

Тестирование проекта разделено на два уровня:

1. обработка отдельных отзывов;
2. групповая аналитика.

Проверяются:

- тональность;
- тип обращения;
- темы;
- критичность;
- необходимость эскалации;
- соблюдение бизнес-правил;
- отсутствие опасных или неподтверждённых обещаний;
- работа с персональными данными;
- корректность количественной статистики.

---

# 2. Тестирование отдельных отзывов

Для автоматической проверки используется файл:

```text
tests/test_assistant.py
```

Тест содержит пять основных сценариев.

## TEST 01 — Опасная неисправность

Вход:

```text
Чайник начал искрить и появился запах гари.
```

Проверяется:

```text
Тональность: negative
Тип обращения: complaint
Темы: quality
Критичность: high
Эскалация: yes
```

Дополнительно проверяется, чтобы ассистент:

- не диагностировал неисправность;
- не утверждал, что проверка уже проведена;
- не обещал выполненное действие от имени компании.

---

## TEST 02 — Смешанный отзыв

Вход:

```text
Холодильник отличный, работает хорошо,
но курьер опоздал на четыре часа и даже не извинился.
```

Проверяется:

```text
Тональность: mixed
Тип обращения: mixed
Темы: product, delivery, service
Критичность: medium
Эскалация: no
```

Этот сценарий проверяет способность модели учитывать одновременно положительную и отрицательную части отзыва.

---

## TEST 03 — Требование компенсации

Вход:

```text
Курьер опоздал на пять часов.
Я потерял весь день.
Требую скидку 30 процентов и компенсацию
за потраченное время.
```

Проверяется:

```text
Тональность: negative
Тип обращения: complaint
Темы: delivery, compensation
Критичность: high
Эскалация: yes
```

Также проверяется отсутствие формулировок, обещающих:

- скидку;
- выплату компенсации;
- уже выполненную передачу обращения.

---

## TEST 04 — Неясная жалоба

Вход:

```text
Ужасный магазин.
Больше никогда у вас ничего не куплю.
Полное разочарование.
```

Проверяется:

```text
Тональность: negative
Тип обращения: complaint
Темы: other
Эскалация: no
```

Ассистент не должен придумывать конкретную причину недовольства.

Например, без оснований нельзя утверждать, что проблема связана с:

```text
delivery
quality
service
```

---

## TEST 05 — Персональные данные

В тестовом отзыве содержатся:

- имя;
- номер телефона;
- информация о недоставленном заказе;
- жалоба на отсутствие ответа.

Проверяется:

```text
Тональность: negative
Тип обращения: complaint
Темы: delivery, service, privacy
Критичность: high
Эскалация: yes
```

Дополнительно проверяется, что номер телефона не повторяется в проекте публичного ответа.

# 4. Тестирование групповой аналитики

Для проверки группового анализа используется:

```text
tests/test_analytics.py
```

Тестовая выборка состоит из шести отзывов:

```text
1. Холодильник отличный, доставили быстро, всё понравилось.

2. Стиральная машина приехала с мятой коробкой,
   но сам товар работает.

3. Курьер опоздал на пять часов и даже не извинился.

4. Телевизор перестал включаться через неделю после покупки.

5. Спасибо менеджеру, всё подробно объяснил
   и помог выбрать товар.

6. Чайник начал искрить и появился запах гари.
```

---

# 5. Что проверяет групповой тест

Для каждого отзыва сначала выполняется индивидуальная классификация.

После этого проверяются:

- отдельные критические сценарии;
- количество отзывов;
- распределение по тональности;
- количество упоминаний тем;
- количество high-criticality случаев;
- количество обращений с эскалацией.

Ожидаемые основные показатели:

```text
Всего отзывов: 6

Тональность:
positive — 2
mixed — 1
negative — 3

High-criticality: 1
Эскалаций: 2
```

# 7. Проблемы, обнаруженные во время разработки

Тестирование использовалось не только для финальной проверки, но и для улучшения архитектуры проекта.

## Проблема 1 — потеря дополнительной темы

При тестировании смешанного отзыва:

```text
Холодильник отличный, работает хорошо,
но курьер опоздал на четыре часа и даже не извинился.
```

первоначально определялись только темы:

```text
product, delivery
```

При этом замечание об отсутствии извинений курьера относится также к качеству обслуживания.

После корректировки правил итоговая классификация стала:

```text
product, delivery, service
```

---

## Проблема 2 — неподтверждённые действия в ответе

На раннем этапе модель могла использовать формулировки вида:

```text
Мы передадим ваше обращение.
```

Но ассистент не подключён к CRM или службе поддержки и фактически не выполняет такое действие.

Поэтому системные правила были усилены.

Теперь ассистент должен формулировать следующий шаг как рекомендацию или необходимость:

```text
Ситуация требует рассмотрения ответственным сотрудником.
```

а не утверждать, что действие уже выполнено.

---

## Проблема 3 — компенсация могла интерпретироваться слишком свободно

При жалобах на доставку модель могла связывать негативный отзыв с темой компенсации даже в случаях, когда клиент её не требовал.

Было добавлено правило:

```text
compensation
```

используется только тогда, когда клиент явно:

- требует компенсацию;
- требует скидку;
- просит возместить ущерб;
- поднимает аналогичный финансовый вопрос.

---

## Проблема 4 — нестабильность количественной аналитики

Первоначально LLM получала несколько отзывов сразу и самостоятельно формировала статистику.

Это приводило к риску:

- неправильного подсчёта тем;
- неверного количества отзывов;
- появления тем, которых фактически не было;
- несоответствия текста сводки исходным классификациям.

Архитектура была изменена.

Теперь используется схема:

```text
Отзывы
   ↓
Классификация каждого отзыва
   ↓
Бизнес-правила Python
   ↓
Расчёт статистики Python
   ↓
Готовые показатели
   ↓
LLM формирует только текстовую сводку
```

Таким образом, количественная аналитика больше не зависит от способности LLM самостоятельно считать элементы выборки.

---

## Проблема 5 — JSON-ответ модели

При реализации структурированной классификации модель могла возвращать JSON внутри Markdown-блока:

```text
```json
{
    ...
}
```
```

Это мешало прямому разбору ответа через JSON-парсер.

Обработка была скорректирована так, чтобы корректно извлекать структурированный результат.

---

## Проблема 6 — различие между обычной и опасной неисправностью

Необходимо было разделить:

```text
Телевизор перестал включаться.
```

и:

```text
Чайник искрит и пахнет гарью.
```

Первый случай:

```text
medium / escalation=yes
```

Второй:

```text
high / escalation=yes
```

Для этого критические признаки были закреплены отдельными бизнес-правилами.

---

# 8. Почему бизнес-правила вынесены в Python

LLM хорошо подходит для:

- понимания естественного языка;
- определения смысла обращения;
- выделения тем;
- генерации текста.

Но критически важные правила не должны полностью зависеть от вероятностного ответа модели.

Поэтому часть логики реализована программно.

Примеры:

```text
опасная неисправность → high
требование компенсации → high
товар не доставлен → high
юридическая угроза → high
```

Это делает поведение ассистента более предсказуемым.

---

# 9. Принцип тестирования после обновлений

После изменения:

- системного промпта;
- базы знаний;
- бизнес-правил;
- классификатора;
- аналитики;

необходимо выполнить оба теста:

```powershell
python tests\test_assistant.py
python tests\test_analytics.py
```

Ожидаемый результат:

```text
5/5 PASS
GROUP ANALYTICS PASS
```

Если хотя бы один тест не проходит, изменение необходимо проверить до публикации новой версии.

---

# 10. Возможное развитие тестирования

Для дальнейшего развития проекта можно добавить:

- больше граничных сценариев;
- автоматические unit-тесты без обращения к API;
- mock-ответы OpenAI API;
- проверку большого набора отзывов;
- тестирование устойчивости к нестандартным формулировкам;
- тестирование длинных отзывов;
- оценку стоимости API-запросов;
- логирование результатов тестов;
- CI-проверку при каждом обновлении GitHub-репозитория.

# 11. Итог

Финальная версия Review AI Assistant успешно проходит два уровня проверки:

```text
Одиночные сценарии:
5/5 PASS

Групповая аналитика:
PASS
```

Тестирование помогло не только проверить готовое решение, но и изменить архитектуру проекта:

```text
LLM → понимание текста
Python → обязательные бизнес-правила
Python → количественная статистика
LLM → человекочитаемая аналитика
```

Такое разделение делает результат более стабильным, контролируемым и пригодным для дальнейшего развития.
